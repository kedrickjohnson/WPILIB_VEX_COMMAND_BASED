Because the simulator is just Java, robot code can be unit tested like any other code: build a subsystem on simulated hardware, run the scheduler, check what happened. GitHub Actions then runs those tests, and both simulators, on every push.

A test

Tests go in src/test/java and use JUnit 4. Each test gets a fresh simulated brain and scheduler:

public class ClampTest {
    private SimHardware sim;

    @Before
    public void setUp() {
        sim = new SimHardware();
        HAL.set(sim);
        CommandScheduler.resetInstance();          // forget subsystems from other tests
        CommandScheduler.getInstance().setRobotEnabled(true);
    }

    private void run(double seconds) {
        for (int i = 0; i < Math.round(seconds / 0.010); i++) {
            CommandScheduler.getInstance().run();
            sim.clock().sleepUntil(sim.clock().nowSeconds() + 0.010);
        }
    }

    @Test
    public void clampsWhenTheGoalArrives() {
        ExampleClamp clamp = new ExampleClamp();
        clamp.clampWhenGoalArrivesCommand().schedule();
        run(0.2);
        assertFalse(sim.getAdiPort('B').isOn());
        sim.getAdiPort('A').setPressed(true);      // goal hits the switch
        run(0.1);
        assertTrue(sim.getAdiPort('B').isOn());
    }
}

Add JUnit to the robot's build.gradle.kts and run ./gradlew test:

dependencies {
    testImplementation("junit:junit:4.13.2")
}
tasks.test { useJUnit() }

Good things to test: that an auto ends (and roughly where), that a mechanism stops at its limit switch, that a button binding schedules the right command, that a command handles a sensor reading "nothing". The library's own tests in vexlib/src/test are examples of all of these.

Continuous integration

The repository has two GitHub Actions workflows in .github/workflows:

WorkflowRuns onDoes
build.ymlEvery push to main and every pull requestBuilds everything, runs the library's tests, runs the template, Clawbot and docs simulators (failing if an auto doesn't finish), tests the VS Code extension, and builds the docs site (failing on broken links).
release.ymlA tag like v0.2.0Publishes that VexLib version to docs/maven, regenerates the vendordep JSON and API reference, commits them, and attaches the VS Code extension to a GitHub release.

Copy build.yml into your own robot's repository (changing the Gradle tasks to build and simulate) and you'll know within minutes whether a change broke something.

Releasing a new VexLib

  1. Change vexlibVersion in gradle.properties (and the extension's version in vscode-extension/package.json), commit, push.
  2. Tag it: git tag v0.2.0 && git push origin v0.2.0.
  3. The release workflow does the rest. Teams see the new version under VEX: Manage Vendor Libraries → Check for updates.
